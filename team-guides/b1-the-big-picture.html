The big picture

GitHub's words make more sense next to something you may already know: a shared document in Microsoft Word with its Track Changes feature switched on. Read this once, and the rest of the guides will feel like steps you already understand.

First, Microsoft Word's Track Changes

Microsoft Word, the word processor, has a feature called Track Changes (on the Review tab). When it's switched on, Word no longer quietly overwrites the text. Every edit you make is marked: deleted words are struck through, new words are underlined, and each mark carries your name. Someone else can then read through your marked edits, leave comments in the margin, and accept or reject each change. Clicking Accept All Changes folds them into the finished document.

You don't need to have used it. The point is the habit it builds: you edit, someone checks, and only then does your edit become part of the document everyone relies on.

Now picture the team using it

Four people are writing one Microsoft Word document. Everyone needs to edit it, but nobody should be able to wreck it, and nobody wants to wait their turn. So each person works on their own copy with Track Changes on, hands it to a teammate to check, and only the accepted changes go into the master copy. GitHub works the same way. It just uses different names for each part, and the table below matches them up.

"Pull" means two different things

You seeIt meansWhich way it goes
Pull (Source Control → Pull)Download the latest shared version onto your computer.GitHub → you
Pull requestAsk the team to accept your changes into main.You → main

If a guide says "pull", it means the first. If it says "pull request", it means the second. GitLab calls a pull request a "merge request". Same thing.

One change, start to finish

Here is the whole route with a real task: Oana has a card to collect interface screenshots.

  1. She starts from the latest main So her copy matches what the team has agreed so far (D1).
  2. She makes a branch Named after her card, so everyone can see what it's for (D2).
  3. She adds her files and commits Checkpoints she can come back to (B3).
  4. She pushes and opens a pull request Her branch is now on GitHub, and she asks Phil to review it (B4).
  5. Phil reviews and merges Her work is now in main. Everyone else's next "pull" brings it down to their computer (E1, E2).

Why it works this way

Every change is seen by a second person before it becomes part of the shared version, and every mistake is confined to someone's own branch. Main is protected, so nobody can push to it directly, Phil included. That sounds like extra work. For a team that has never worked together, it's what stops one person's slip from becoming everyone's problem on Wednesday afternoon.

Done when: you can say the five stages in order (branch, commit, push, pull request and review, merge) and explain the two meanings of "pull".
